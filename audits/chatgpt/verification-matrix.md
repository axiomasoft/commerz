## 2. Обязательные интеграционные сценарии до первого публичного релиза

### Каталог и свойства

- Простое создание автоматически дает один валидный вариант; повтор идемпотентного запроса не создает второй.
- Дубликат комбинации осей отклоняется; смена перевода опции не меняет идентичность SKU.
- Оси не дублируются как второй канонический источник EAV.
- У товара невозможно значение схемы другого свойства; atom/group другого владельца запрещен.
- Integer/Decimal/Boolean/Date сохраняются без неявных строковых/float-преобразований.
- Measurement не принимает несовместимую семью единиц; преобразование и округление воспроизводимы.
- Dictionary option нельзя применить к чужому справочнику.
- Missing, explicit clear, empty set, false и zero проходят разные пути.
- Fallback возвращает правильный источник значения; версия политики включена в инвалидирование.
- Изменение типа/кратности идет через draft schema → validation → migration → reindex → activate.
- Удаленный элемент справочника не ломает исторические карточки/снапшоты; действует архивирование/замена.
- Перемещение категории не создает цикл даже при конкурентных перемещениях.
- Композитный table сохраняет row identity при перестановке строк; фильтр не соединяет разные строки.
- Превышение лимита глубины/количества свойств/длины keyword отклоняется предсказуемой ошибкой.

### Поиск

- Цвет+размер+публикация+наличие+цена выполняются на одном подходящем варианте.
- Product-level свойства и унаследованные variant-значения разрешаются одинаково в API карточки и поиске.
- any/all/none для наборов и exists/missing/empty имеют утвержденную таблицу истинности.
- Facet counts считают нужную сущность DISTINCT; self-exclusion снимает только свой фасет.
- Фасет никогда не раскрывает скрытые/private свойства или неопубликованные товары другого канала.
- Numeric sort работает по каноническому числу; enum sort — по явно выбранному порядку.
- Multi-value sort требует reducer; null ordering и tie-breaker дают стабильную пагинацию.
- Цена сортировки относится к подходящим продаваемым вариантам, валюте, количеству и сегменту.
- Все поддерживаемые адаптеры проходят один набор golden queries на одинаковых фикстурах.
- Для движков с approximate facet counts точность явно отмечена, а не объявлена exact.
- Полная перестройка индекса при продолжающейся записи не теряет updates/deletes.
- Старое событие не воскрешает удаленную карточку; tombstone имеет версию.
- Проверено поведение delta-событий при дыре последовательности: обнаружение и восстановление.

### Склад

- 100 одновременных запросов на одну единицу из двух каналов → один принятый резерв.
- Тот же сценарий через два пересекающихся stock pool → тот же результат.
- Для разных приложений с общим запасом проверен центральный арбитраж или непересекающиеся квоты; локальный тест одной БД не объявляется доказательством межсистемной корректности.
- Повтор одного idempotency key возвращает прежний результат; другой payload с тем же ключом дает конфликт.
- Ошибка второй позиции многокомпонентного заказа откатывает резерв первой.
- Детерминированная сортировка блокировок уменьшает риск deadlock; повторяется вся команда с тем же ключом.
- Параллельные receive/reserve/count/ship не создают потерянных обновлений.
- Резервирование не меняет physical; подтверждение не удваивает reserve.
- Частичные shipment/cancel суммарно не превышают allocation.
- Expire/confirm гонка заканчивается одним допустимым состоянием.
- При недостаче physical < reserved обязательства не исчезают; доступность 0; создан discrepancy.
- Передача товара не делает его одновременно доступным на исходном и целевом складе.
- Частичная приемка/потеря в пути корректно закрывает transit.
- Пакеты и виртуальные наборы делят общий InventoryItem; повторные требования агрегируются.
- Изменение рецепта комплекта не меняет состав уже созданного резерва/заказа.
- Co-location/split-fulfillment режимы дают разные ожидаемые результаты.
- Проведенный документ не изменяется тихо; повтор проводки не добавляет ledger entry.
- Reconciliation сопоставляет физический ledger с on_hand, reserve log/allocations с reserved.
- Смена базовой единицы после движений отклоняется либо проводится отдельной документированной миграцией.
- Отключение склада в канале не теряет уже существующие обязательства и не создает гонку новой продажи.

### 1С и интеграции

- Реальные fixtures минимум из выбранной конфигурации, включая обычный товар, характеристику, комплект/упаковку, несколько цен и складов.
- Одинаковый внешний id из двух подключений не конфликтует.
- Повтор full/delta/import batch не дублирует карточки, цены, проводки.
- Отсутствие записи в delta ничего не удаляет; failed full не запускает массовую деактивацию.
- Отсутствие поля и explicit clear различаются согласно профилю.
- Price type, unit conversion, classifier/options и warehouse-id отображаются без SKU-эвристик.
- Старый снимок остатка не возвращает проданный товар; признанные 1С резервы не вычитаются дважды.
- Неполный/противоречивый causal checkpoint переводит импорт в явный конфликт, а не применяет last-write-wins.
- Падение после записи БД до отправки подтверждения допускает безопасный повтор.
- Частичная ошибка батча сохраняет отчет и checkpoint, но не считает full успешным.
- XML/архивы: запрещены внешние сущности, path traversal, oversized/zip bomb, недопустимые URL; проверены квоты и таймауты.
- Секреты/персональные данные не попадают в публичный error log и поисковую проекцию.

### Пакет и эксплуатация

- CI на каждой заявленной комбинации PHP/Laravel/СУБД, не только SQLite.
- Установка с существующими таблицами приложения не создает конфликт имен/route/config.
- Core работает без admin/UI и без конкретной App\\Models\\User.
- Worker последовательно обрабатывает задачи двух каналов без утечки глобального context.
- Миграция версии N→N+1 протестирована на заполненной БД; старые опубликованные миграции не редактируются.
- Outbox доставляется повторно безопасно; падение publisher после отправки до отметки published не удваивает эффект.
- Механизмы repair/rebuild имеют dry-run, отчет и права доступа.
- Backups/restore восстанавливают не только каталог, но ledger, reservations, idempotency receipts, source checkpoints.

## 3. Нагрузочные испытания, которые еще НЕ выполнены

Выбрать три репрезентативных профиля, а не один абстрактный «миллион товаров»:

1. Большое число простых SKU, мало свойств, частые обновления запасов.
2. Среднее число карточек, много вариантов и многозначных фасетов.
3. Сложные B2B-свойства, составные таблицы, несколько прайсов и каналов.

В каждом зафиксировать: количество товаров/вариантов, среднее и p95 числа атрибутов/опций/строк composite, селективность фасетов, число каналов/локалей/складов, долю обновлений stock/price/content, частоту запросов/импорта и ожидаемый SLA.

Измерять: p50/p95/p99 поиска и резерва; число SQL/чтений; планы запросов; lock wait/deadlocks; CPU/память; размер индексов; скорость full/delta import; write amplification; index lag; время recovery/reindex; поведение деградации.

SLA и пороги задаются требованиями проекта, а не выдаются как измеренные характеристики этой архитектуры.
