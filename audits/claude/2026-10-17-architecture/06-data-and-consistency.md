# 06. Данные, инварианты, конкурентность

Объект: `docs/architecture/{data,invariants}.md`, 32 миграции, протоколы блокировок, outbox, idempotency,
пагинация. Находки `DAT-xx`.

## 1. Оценка подхода

Это сильнейшая сторона проекта. Реестр из 30+ инвариантов, у каждого — **один владелец, одна точка
обеспечения, закрытый обход и тест**; глобальный порядок блокировок с детализацией по пакетам; конкурентные
тесты N процессов на реальной PostgreSQL (SQLite «никогда не доказывает блокировки» — верно). Отдельно
отмечу:

- выбор режимов блокировок (`FOR NO KEY UPDATE` вместо `FOR UPDATE`, потому что вставка FK берёт
  `FOR KEY SHARE`; `KEY SHARE` для потребителей лимита против `FOR UPDATE` для изменения определения);
- «счётчик существует только пока задан лимит» — нет горячих строк у безлимитных акций/купонов;
- `EXCLUDE USING gist` для окон цен и ставок, `UNIQUE NULLS NOT DISTINCT` для членов зон;
- reconcile-команды только читают на `REPEATABLE READ`, ремонтируют лишь производные (`reserved`);
- разность `on_hand − reserved − safety_stock` в `numeric`, чтобы не выйти за int64;
- отказ от автоматического ретрая — вызывающий повторяет операцию целиком.

## 2. Находки

### DAT-01 · Medium · Порядок блокировок обеспечивается соглашением

Глобальный порядок `cart/order → документы → уровни склада → купоны → акции → использования → платежи →
возвраты` описан и соблюдён в пакетах, но хост, комбинирующий команды в одной `Transactions::run`
(документировано как допустимое), легко нарушит его (например, сначала `Coupons::setLimit`, затем
`Checkout::place`). Ошибка проявится как `40P01`/`55P03` под нагрузкой.

Рекомендация: «lock-order guard» в debug/testing-режиме — каждый протокол блокировки объявляет класс ресурса
(`LockClass::StockLevel`, …) через ядро (`$this->locks->acquire(LockClass::Coupon, …)`), guard хранит
последний класс в транзакции и бросает `LogicException` при движении «назад». В production — no-op.
Это превращает таблицу из `invariants.md` в исполняемую спецификацию.

### DAT-02 · Medium · Снимки заказа в JSONB затрудняют аналитику

`cmz_orders.order_adjustments`, `delivery_adjustments`, `delivery_tax_lines`, `cmz_order_lines.adjustments`,
`tax_lines` — JSONB с кодеком sales. Это корректно для ORD-02, но отчёты «скидка по акции × период»,
«НДС по ставкам за месяц» требуют JSONB-разворота на каждом запросе. `cmz_promotion_usages` частично закрывает
первый вопрос, но в пакете promotions.

Рекомендация: нормализованные дочерние таблицы снимка (`cmz_order_adjustments(order_id, line_id, target,
source, promotion_ref, amount_minor, …)`, `cmz_order_tax_lines`) — пишет тот же единственный `OrderWriter`;
JSONB можно оставить как кэш чтения или убрать.

### DAT-03 · Medium · Нет стратегии роста журналов

Append-only таблицы `cmz_stock_movements`, `cmz_order_events`, `cmz_outbox_messages`, `cmz_payment_events`,
`cmz_promotion_usages` растут без ограничений; outbox и receipts чистятся, остальные — нет (правильно, это
история), но нет ни партиционирования по времени, ни архивации, ни рекомендаций в `operations/`. Индексы под
чтение истории есть (`stock_movements (stock_level_id, id)`, `(stock_item_id, id)`, `reference`;
`order_events (order_id, id)`), под выборки «за период» (`stock_movements.occurred_at`,
`order_events.created_at`) — нет.

Рекомендация: документ «Data lifecycle»: декларативное партиционирование по месяцу для movements/events
(PostgreSQL 16 поддерживает FK на партиционированные таблицы), `commerz:archive` для выгрузки старых партиций.

### DAT-04 · Low · Курсоры пагинации не привязаны к запросу

`Cursor` — base64 позиции без подписи и без хэша фильтров (`Pagination/Cursor.php`). Курсор от одного
запроса можно подставить в другой (другие фильтры/сортировка) — результат молча неверен. Нет обратной
пагинации (`before/last`) и количества.

Рекомендация: токен = base64(json{v, position, queryHash}) + HMAC с `APP_KEY`; `fromToken` проверяет хэш
запроса; добавить `before`.

### DAT-05 · Low · Время UUIDv7 зависит от часов узла

Генерация в приложении (D7) на нескольких узлах с рассинхроном часов даёт немонотонные id между узлами.
Для keyset по `(created_at, id)` это не ошибка, но `id ASC` как «порядок создания» (в reconcile/отчётах) —
приблизительный. Задокументировать; критичные порядки брать из `identity`-журналов.

### DAT-06 · Low · Outbox prune делит TTL с receipts

См. KRN-08 п.4: `commerz:operations:prune` удаляет доставленные сообщения по `receipt_ttl_days`. Хранение
outbox для аудита/повторного проигрывания обычно отличается (7 дней vs 30).

### DAT-07 · Info · Мультитенантность через схему

`SchemaFingerprint` ищет таблицы в `current_schema()`, `TableNames` не квалифицирует схему — значит, модель
«схема на арендатора» (`search_path`) работает из коробки, в дополнение к «соединение/БД на арендатора» (D6).
Стоит явно описать в `docs/operations/` (и протестировать: два арендатора, одна БД, разные схемы, разные
префиксы).

## 3. Проверка утверждений invariants.md выборочно

| Утверждение | Проверено | Результат |
|---|---|---|
| `Outbox::record` требует открытой транзакции | `DatabaseOutbox::record` | ✔ `LogicException` при уровне 0 |
| Relay отказывается работать внутри транзакции | `OutboxRelay::relay` | ✔ |
| Receipts: нет read-then-write | `DatabaseOperationReceipts::once` | ✔ `INSERT … ON CONFLICT DO NOTHING RETURNING`, затем `SELECT … FOR UPDATE` |
| Вложенный `run` — savepoint, откат своих записей | `DatabaseTransactions::run` | ✔, с обходом бага уровня Laravel |
| Размещение: чтение вне транзакции, запись в порядке receipt → cart → order → stock → usage → outbox | `OrderPlacement` | ✔ ровно так; проверка `cart.version` под блокировкой |
| Только физические строки резервируются | `OrderPlacement::reserveLines` | ✔ — но это проблема дизайна (PKG-SAL-04) |
| Стадии котировки не пишут в БД | соглашение | ◐ не проверяется; стадии могут резолвить любые сервисы из контейнера |
| EXT-01 «сбой плагина не оставляет половину мутации» | котировка до транзакции | ✔ для стадий; ✘ для итогов (KRN-01: результат стадии не проверяется) |
