# Decision log

Accepted architecture decisions of Commerz. Each entry states the decision and
the one-line reason; options and evidence live in plan `PLAN1`
(`plans/2026.10.08-№1-COMMERZ-FOUNDATION/`) and the research corpus. A new
decision gets the next number; a reversed decision keeps its number and is
marked `superseded by Dn`.

Decided by: the owner for D1; the agent under the owner's delegation (see
`CLAUDE.md`, "Owner delegation") for the rest.

| ID | Status | Decision | Reason |
|---|---|---|---|
| D1 | accepted | Stack: PHP ^8.4, Laravel ^13 only. | Owner's instruction; one compatibility matrix on the current stack. |
| D2 | accepted | Database: PostgreSQL ≥ 16 only (CI on 17). | Stock, price and limit invariants rely on `EXCLUDE`, partial unique indexes, `jsonb` and transactional DDL; CoreX is PostgreSQL-only. MySQL only by a later decision with a real consumer. |
| D3 | accepted | Packages: core + catalog, inventory, pricing, promotions, shipping, sales (+ full, testkit); feature packages depend only on the core and interact through core ports. | Each package installs alone (stock without catalog, CRM sales without catalog) and P2–P7 develop in parallel. |
| D4 | accepted | Stores and channels are a core module (`Commerz::stores()`, `channels()`). | The channel is part of every operation's context; a separate package would become a second core. |
| D5 | accepted | Coupons are a module of `commerz-promotions`, plugged in as activator `coupon` through the public SPI. | Keeps the promotion engine coupon-agnostic (SPI dogfooding) without an extra release unit. |
| D6 | accepted | Tenancy: no `tenant_id`; isolation by the connection or database the host provides; many stores and channels per database. | Matches CoreX ADR-004 and Flex CRM and keeps keys simple; shared-schema SaaS would need its own plan before new migrations. |
| D7 | accepted | Keys: application-generated UUIDv7; append-only journals `bigint identity`; host and cross-package references `*_ref varchar(191)` `type:id`. | Ecosystem canon (CoreX ADR-003, Chatom); IDs exist before `INSERT`; no configurable strategy matrix. |
| D8 | accepted | Money: `int` minor units + currency, `brick/math` with explicit rounding, largest-remainder allocation; quantities `int` in the stock item's base unit; rates in basis points. | Exact sums and simple invariants without floats; weighted goods in g/mm with a sale step. |
| D9 | accepted | Product data: operational fields as columns, variant axes relational (`UNIQUE option_signature`), other attributes as a JSONB document validated by `attribute_type` codecs, filterable ones projected synchronously into `cmz_attribute_index` with `variant_id`. | One-row product reads, correct facets right after save, new attributes without migrations. |
| D10 | accepted | Stock: `cmz_stock_levels` (on_hand, reserved) + append-only `cmz_stock_movements` + `cmz_stock_reservations` by demand; reserve with a conditional `UPDATE`; `ReservationTiming` default `OnOrderPlaced`, option `OnCheckout` with TTL. | Simple and proven under concurrency; matches commercetools reserve-on-order and the Vendure 3.7.4 lesson. |
| D11 | accepted | `PlaceOrder` is one local transaction (receipt → order snapshot → reserve → consume usage → outbox) in the global lock order; payment is a separate command after commit; `OrderState`, `PaymentState`, `FulfillmentState` are independent enums. | All packages share one connection, so no saga is needed and no network call runs under locks. |
| D12 | accepted | API: a root `final readonly` API class per package + facade; domain contracts; command/query DTOs → views/results; Eloquent only in `Internal/Models`; no model swapping. | Clean ecosystem API with Laravel development speed; hidden models can be replaced later without a BC break. |
| D13 | accepted | Promotion limits: entering a code never consumes; consumption happens in the `PlaceOrder` transaction; restore on expiry of an unpaid order and cancellation before payment (`promotions.restore_on`). | No claim phase; matches Saleor and commercetools; abuse is bounded by payment due time and auto-cancel. |
| D14 | accepted | Shipping owns zones, methods, rates, carriers, `DeliveryOptions` and `ShipmentBooking`; sales owns order fulfillments (shipped lines, reservation consumption, tracking). | "Delivery costs 300" is a quote; "parcel shipped" is order bookkeeping that keeps `ordered = cancelled + fulfilled + outstanding` with the order owner. |
| D15 | accepted | Stackable promotions within one stage apply sequentially to the already reduced price (10 % + 5 % = 14.5 %), ordered by `priority DESC, key ASC`. | Totals never go negative and the result is predictable and budget-safe; the owner may revisit before P5. |
| D16 | accepted | Delivery strategy: rolling wave — execute P1, detail P2–P7 in one pass against the real kernel, run them as parallel lanes, then detail and execute P8. | Designs of feature packages are checked against real code, not guesses. |
| D17 | accepted | Catalog axes are a separate module `Catalog::options()`; a variant's `option_signature` is built from the sorted UUIDs of its option values; attribute `type` and `config` are immutable after `define` (name, `filterable`, status and new choices change); choices and option values are never deleted; every sellable is a variant (a simple product has the empty signature); the catalog holds no prices. | An option is not a specification; CAT-01 holds literally over normalized IDs; no live type migration and no type-change race. |
| D18 | accepted | After-commit events are the public core contract `Commerz\Operations\Contracts\CommittedEvents::dispatch()` (immediately outside a transaction); stores moved onto it. | Every feature package needs the same policy; one contract instead of per-package copies. |
| D19 | accepted | Catalog search is `Products::list(ListProducts)` with typed `AttributeFilter` / `VariantFilter` compiled to SQL (same-variant semantics, keyset by `handle`); no indexer port and no facet counts in 0.1. | SQL filters prove CAT-03 now; an indexer SPI is added later without breaking SemVer. |
| D20 | accepted | Nested `Transactions::run` uses a savepoint on the Commerz connection; the outer transaction retains its lock timeout and final commit. A failed operation rolls back its writes and pending events even when the host catches the exception. Outbox relay requires no open transaction. | Audit regressions demonstrated poisoned receipt keys and partial catalog updates under the former ambient join; enforce atomicity once in the kernel before P3–P7. |
| D21 | accepted | Inventory v0.1: a reservation header per demand (`UNIQUE`, generation) with lines per (sellable, item, location) in sellable units and a `quantity_per_unit` snapshot; kits are several links, one kit unit comes from one location; item policy `tracked \| backorder \| untracked`; unlinked sellables are unavailable by default; allocation is the `allocation_strategy` SPI (`priority`, `single_location`) over locked levels with a validated plan; lock order document → header → levels (one ordered `FOR NO KEY UPDATE`) → lines, foreign headers `SKIP LOCKED` only; `adjust` and `count` accept physical truth below the reservation and publish `StockShortfall`; `count` is a compare-and-set on `expectedOnHand`; a transfer is a source reservation → `transfer_out` → `transfer_in` (partial receipt, lost) without a transit location; reconcile repairs only `reserved`. | One lock hierarchy keeps INV-02..06 deadlock-free; kits and policies cover shops and CRMs with one model; physical reality is never refused, a shortfall is signalled (Vendure 3.7.4, Shopify). |
| D22 | accepted | Core port `Ports\Stock` grows additively in P3: `StockReturns::restock(RestockStock)` (idempotent per reference, joins the caller's transaction) and `ConsumeReservation::$locationCode`; `UnlimitedStock` and `FakeStock` implement them. | Sales (P7) needs restock and location-bound shipment through core ports only; adding them before 0.1 lets P3 test them on a real warehouse. |
| D23 | accepted | Core grows additively in P4: `QuoteState::allocatedOrderAdjustments()` and `deliveryNet()` (the one order-discount allocation, shared by `totals` and `tax`), `Money::includedPart(Rate, RoundingMode)`, `ConstraintNames::exclusion` and `CommerzMigration::exclude`. | Tax bases equal the settled lines to the minor unit (TAX-02, PRM-02); a copy of the allocation in pricing would drift. |
| D24 | accepted | Pricing v0.1: price = list priority DESC → lowest applicable amount → group → min quantity DESC → code → id; `TaxInclusion` `Included \| Excluded \| AsChannel`; gross prices are fixed and tax is carved out; tax after all discounts, rounded per line; a tax-exempt customer gets no tax lines and no price change; zone by delivery address `(country, region)`, else `default_zone`, else no tax; dated rate windows, several non-compound codes; a class without a rate in its zone → `TaxRateNotFound` (fail-closed). | The seller's priority wins, the buyer is protected within a level (Magento); a VAT change (RU 22 % from 2026-01-01) is a data change; a missing rate never silently under-taxes. |
| D25 | accepted | Core grows additively in P5: `QuoteResult::appliedPromotions()` folds a quote's adjustments into one `AppliedPromotion` per promotion id (own line adjustments, then declared order and delivery adjustments; the per-line shares of order adjustments are not counted again). | `PromotionUsage::consume` (sales, P7) and the promotions tests need one fold; two copies would double-count order shares and let a budget drift from the discount actually given (PRM-02). |
| D26 | accepted | Promotions v0.1: a promotion has an explicit, immutable stage (`catalog \| cart \| delivery`) and every rule declares the stages it may be used in; within a stage `priority DESC, code ASC`, sequential application (D15), `Stacking::Stackable \| Exclusive` and `stopFurther`; conditions run in two passes (line filters, then qualifiers); a promotion applies whole or not at all, with discounts clamped at zero; one engine session per `QuoteInput` serves the three stages; the quote records rejections only for presented codes and `explain` gives the full verdict; channels are an assignment of the promotion, there is no `channel.in` condition; `buy_x_get_y` draws from one pool of the cheapest units. | The outcome is deterministic and explainable (commercetools / Magento semantics), the stages never reload or disagree, an unknown rule fails closed, and the engine stays coupon-agnostic (D5). |
| D27 | accepted | Limit spending: a counter is kept only while its limit is set; `consume` takes the redemption header (`UNIQUE(order_ref)` + fingerprint), then coupons → promotions → customer usages by `id ASC`, `FOR KEY SHARE` plus conditional `UPDATE` / `ON CONFLICT DO UPDATE … WHERE`; definition mutations take `FOR UPDATE` and recount from the consumed usages; `consume` re-checks the status, not the window; a guest cannot use a per-customer limit; `restore` follows `promotions.restore_on` and is idempotent. | An unlimited promotion is never a hot row; KEY SHARE vs FOR UPDATE makes limit changes and pauses exact without serializing consumers; fixed order prevents 40P01; a guest is fail-closed. |
| D28 | accepted | Shipping model: overlapping zones (members country, region, postal prefix) ranked by specificity then code; a tariff per (method, zone, currency) with a `delivery_rate` rule and `free_above`, `tax_included`, `eta_days`; `free_over` is replaced by the field `free_above` on the goods after discounts; one `MethodPricer` serves options and the `delivery` stage; a selected method that cannot deliver fails the quote (`method_unavailable`). | "Moscow" overrides "Russia" without manual priorities; the threshold works with any rule, plugin rules included; an option's price equals the quote's; no order is placed without paid delivery (SHP-01, SHP-02, SHP-06). |
| D29 | accepted | Carrier booking: journal `shipping_bookings` keyed by `reference` (`UNIQUE`, `INSERT … ON CONFLICT`, `FOR UPDATE`, lease, `attempts` fencing); the network is outside any transaction; a timeout is `unknown` and a retry calls `Carrier::find` before booking anew; the same fingerprint returns the stored result, another is `IdempotencyConflict`. | A double label is real money and a real parcel; the guarantee lives in the package that owns the port, not in each adapter or in sales (SHP-03, SHP-04). |
| D30 | accepted | Booking replay and recovery are governed by the journal and its original payload. Current method settings are validated only for a new operation or a fresh attempt after final rejection. A booked replay needs no carrier; recovery uses the original carrier, and an unavailable contribution leaves the outcome unknown and retryable. | Archiving a method or changing its carrier must not strand a possibly existing shipment or deny a stored result; method validation failures roll back the claim before any network call. |
