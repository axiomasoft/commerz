# Свойства и варианты: сравнение способов хранения

2026-10-08. Исследовательский материал. Схема не выбрана; оценки ниже качественные, измерений производительности ещё нет.

Главные источники: [Unbox](analysis-unbox.md), [Lunar/Bazar/Vanilo/Bagisto/Sylius](github-references.md), [Shopify/Magento/Shopware](external-platforms.md), [аудит ChatGPT](chatgpt-audit-review.md). Указанные там файлы и ревизии являются доказательствами фактической реализации референсов. Этот документ сравнивает альтернативы для Commerz.

## 1. Сначала разделить четыре независимые оси

| Ось | Варианты | Типичная ошибка |
|---|---|---|
| Смысл | Описание товара, ось варианта, персонализация, характеристика партии | Хранить всё в одной таблице «характеристики» без owner semantics |
| Семантический тип | Цвет, размер, масса, измерение, ссылка, сертификат | Считать строковый цвет равным произвольной строке |
| Представление | string/integer/decimal/reference/object/list | Считать, что decimal column уже определяет единицу и rounding |
| Редактирование | input/select/colorpicker/upload/repeater | Хранить UI control как единственный источник типа данных |

У одного semantic type может быть несколько UI, а один control редактирует множество типов. Все writers — UI, import, API, CLI — должны сходиться на одной нормализации и проверке.

## 2. «Не больше шести» — не одна схема

Можно иметь:

1. Шесть заранее известных бизнес-полей: например длина, ширина, материал, отделка, профиль, класс.
2. Не более шести definitions для каждого типа товара, но имена и типы различаются между семействами.
3. Не более шести осей варианта, плюс сколько угодно описательных характеристик.
4. Шесть generic slots `property_1...property_6`, смысл которых определяется метаданными.
5. Неограниченную таблицу definitions, но текущий бизнес использует только шесть.

Это разные ограничения. По раннему анализу Unbox есть dynamic definitions и relational values; технического `max 6` пока не обнаружено. Поэтому нельзя назвать его схемой шести фиксированных колонок только на основании устного описания. Полное подтверждение — [analysis-unbox.md](analysis-unbox.md).

Количество осей ограничивает глубину комбинации, но число возможных вариантов равно произведению количества значений осей. Для шести осей по десять значений получается 1 000 000, а реально продаваемых сочетаний может быть 30. Хранить и генерировать нужно прежде всего допустимые продаваемые конфигурации; декартово произведение — необязательная операция с лимитом и предпросмотром.

## 3. Вариант A: явные предметные колонки и дочерние таблицы

Пример: семейство industrial_panel имеет конкретные length, width, material reference, finish reference; сложная спецификация сертификата хранится отдельной структурой.

**Плюсы:** ясная семантика, строгие ограничения, простые range filters, предсказуемые индексы, понятные DTO и миграции. Невозможно случайно записать имя материала в поле длины только потому, что оба сериализуются строкой.

**Минусы:** добавление нового вида свойства требует изменения кода/схемы. При множестве несвязанных семейств получается много nullable полей или много таблиц. Общее управление каталогом требует адаптера.

**Где это хороший выбор:** ограниченный известный домен со сложными инвариантами; свойства редко добавляются пользователями; разработчик контролирует эволюцию. Сложность объекта не является аргументом против явной модели — иногда это аргумент в её пользу.

**Для Commerz:** возможный специализированный product-profile adapter. Обязательный общий контракт должен быть минимальным: identity, sellable configuration, сериализуемый snapshot и объявленные query capabilities. Нельзя обещать, что любой произвольный SQL-профиль автоматически поддерживает весь универсальный query DSL.

## 4. Вариант B: generic slots фиксированного числа

Шесть физических пар slot/value с метаданными о смысле каждой позиции.

**Плюсы:** предсказуемое число полей; отдельный индекс по слоту; потенциально удобно для одного действительно стабильного процесса.

**Минусы:** позиция подменяет семантику; разные товары используют третий слот по-разному; сложнее типизация, локализация, multi-value и ссылки. Добавление седьмого свойства становится разрушительным порогом. Индекс `slot_3` может смешивать несопоставимые значения разных типов.

**Вывод:** не считать slots естественным следствием «не больше шести». При известном смысле лучше проверить явные поля; при неизвестном — definitions/value relation. Slots оставляем исследовательским конкурентом, а не рекомендуемым default.

## 5. Вариант C: нормализованные definitions/options/relations

Товар объявляет допустимые свойства, справочник хранит значения, вариант связан с конкретными значениями. Unbox использует близкую форму; Shopware разделяет descriptive properties и variant options.

**Плюсы:** повторное использование options, возможность локализовать label отдельно от стабильного кода, естественное представление enum/multi-select и осей вариантов. Простые связи product→property и offer→value понятны SQL и ORM.

**Минусы:** свободный текст и точные диапазоны требуют дополнительных типов хранения. Нельзя удалять и пересоздавать значения, если ID используются вариантами или историей. Требуется доказать, что value принадлежит нужной definition и выбранной product family.

**Сложный вопрос:** допускаются ли одинаковые display labels в разных properties/магазинах/локалях? Уникальность должна основываться на определении и стабильном коде, а не на глобальном label.

**Для Commerz:** хороший кандидат для variant axes и reference/enum values даже при другом canonical storage описательных характеристик. Разные роли могут иметь разные хранилища без универсального EAV на каждый факт.

## 6. Вариант D: EAV с одним строковым значением

Определение объявляет тип, значение хранится строкой, адаптер интерпретирует его при чтении.

**Плюсы:** простая базовая схема; легко добавлять definition; удобно хранить редкие метаданные.

**Минусы:** range/sort могут стать лексикографическими (`100 < 20`), нужны преобразования, invalid values допускаются при обходе writer, ссылочная целостность слабая. Типовая информация живёт вне самой колонки. Смена семантики может переинтерпретировать всю историю.

**Где допустимо:** редкие неиндексируемые metadata при строгом codec и отсутствии обещания эффективных числовых фильтров.

**Для Commerz:** слабый default для основного каталога с фильтрами; не отвергать для технических строковых attributes, но явно ограничить capabilities.

## 7. Вариант E: typed EAV

Две реализации: отдельные таблицы по physical type (как у Magento) либо одна таблица с отдельными nullable typed columns (близко к Bagisto). Различие влияет на ограничения и запросы.

**Плюсы:** точные сравнения, индексы по типу/definition/value; metadata меняется без новой колонки на каждый атрибут; можно ограничить структуру скаляров.

**Минусы:** много строк, несколько joins/exists на фасеты, сложнее batch reads, локали и scopes увеличивают объём. One-row-many-columns требует согласования payload с типом definition: measurement может включать число и unit, range — две границы; это не универсальное правило «ровно одна non-NULL колонка». Multi-value и nested object нуждаются в ordinal/object identity, а пустая коллекция — в представлении, отличимом от отсутствующего значения.

**Главный конфликт с произвольными плагинами:** конечное множество physical types не покрывает автоматически любой новый semantic type. Возможны четыре честных договора:

1. Новый тип обязан сводиться к одному из встроенных storage kinds.
2. Тип хранит versioned JSON и явно ограничивает фильтры.
3. Плагин владеет дочерней typed table и её жизненным циклом.
4. Canonical value универсально сериализуется, а фильтры идут через отдельную проекцию.

Каждый вариант допустим при ясных границах. Нельзя одновременно обещать «только семь колонок навсегда» и «любой тип автоматически поддержит любой запрос».

## 8. Вариант F: JSON-документ + definitions

Свойства владельца сгруппированы в документ, types/validation объявлены отдельно. Lunar — важный практический референс; подробности его сериализации и рисков — в source review.

**Плюсы:** быстро читать весь набор, легко сохранять составные значения, относительно мало таблиц, удобно версионировать документ как единое целое.

**Минусы:** конкурирующие изменения разных свойств могут конфликтовать на одном документе; ссылочная целостность и scalar constraints переносятся в write boundary; backend-specific JSON querying и индексы влияют на переносимость. «Можно хранить» не означает «можно эффективно искать».

Для долговечных данных нужен стабильный type code; FQCN сериализуемого PHP-класса связывает данные с namespace. Отсутствующий codec не должен превращать значение в молча исчезнувшее поле.

**Для Commerz:** серьёзный конкурент typed EAV, особенно при сложных объектах и чтении карточок. Требует измерить bulk imports, update contention, facets, scope resolution и rebuild индекса.

## 9. Вариант G: canonical values + typed query projection

Каноническая запись выбирается из E/F; индекс хранит нормализованные фильтруемые значения и связи с variant/object. Для простого потребителя можно читать напрямую; для большого каталога строить projection.

**Плюсы:** отделяет удобную запись от запросов, позволяет разные query backends, индексы восстанавливаются. Составной semantic type может проецировать несколько измерений.

**Минусы:** задержка, очередь/rebuild, ревизии и смена формата проекции, два набора операционных процедур. При отсутствии полноценного протокола invalidation можно показывать неверные цены/свойства.

**Условие:** производные значения никогда не редактируются независимо. Для каждой projection row известны owner, source revision, projector version, variant/object identity и scope. Для multi-module карточки отдельно решается версия каждой зависимости.

## 10. Качественная матрица

Высокая оценка означает соответствие конкретному критерию, а не абсолютное превосходство. Здесь нет benchmark score.

| Новые типы без изменения БД | Ограниченно | Ограниченно | Для options | Легко хранить, сложно искать | Через storage contract | Легко хранить | Через codec + projector |

## 11. Инварианты вариантов независимо от хранения

- Комбинация осей нормализуется по стабильным IDs/codes, а не по порядку ввода или отображаемым labels.
- В одном варианте не больше одного значения одной single-value axis; допустимость задаётся definition.
- Уникальность комбинации scoped по product и релевантному контексту. Хеш — ускоритель сравнения, не единственная защита от семантической коллизии без сохранения нормализованного набора.
- Пустая комбинация у простого товара — осмысленный default variant, если выбран этот вариант модели.
- Оси могут иметь запрещённые сочетания: это sparse set, не обязанность создать весь Cartesian product.
- Изменение definition не должно удалять старые offers каскадом без явного плана. Проданные/зарезервированные конфигурации должны остаться интерпретируемыми.
- SKU uniqueness и combination uniqueness — разные ограничения.
- Локализация label не создаёт новый вариант; персонализация заказа не обязана создавать новый SKU.

## 12. Смена типа и публикация определения

Варианты lifecycle: жёстко запретить смену типа при наличии значений; создавать новую definition и mapping; либо поддержать явную versioned migration. Для начального пакета первый или второй подход может оказаться достаточным.

Если нужна живая migration, её протокол должен покрывать: draft → validation existing values → compatibility writers → backfill → index generation → atomic activation → cleanup/retention. Одного status `active` недостаточно: writer со старой схемой может сохранить старое значение между проверкой и активацией.

Нужны measured сценарии: 100 тыс. товаров меняют decimal precision; выбор enum становится multi-select; reference target удалён; units меняют representation; rollback после половины backfill. Это список будущих испытаний, а не уже реализованная поддержка.

## 13. Как принять решение

Сравнивать одинаковую семантику минимум на трёх workload:

| Набор | Что имитирует | Обязательные запросы |
|---|---|---|
| U: ограниченный сложный каталог | Профиль из Unbox после уточнения шести свойств | Карточка, допустимые offers, facet в выбранном shop, изменение option |
| D: разнообразный каталог | Много families и sparse attributes | 3–6 AND filters, range, locale fallback, sameVariant |
| C: составной каталог | Массивы объектов, measures, references | sameObject, UOM normalization, reference existence, codec upgrade |

Данные синтетические и явно помеченные; числа товаров/атрибутов менять параметрами. Сначала сравнить корректность и число запросов, потом latency p50/p95/p99, память, объём storage, write amplification, стоимость rebuild и миграции. Фиксировать движок, версию, индексы, ресурсы и seed. Не публиковать «JSON быстрее EAV» без этих условий.

До результатов разумно сохранить два ведущих кандидата: typed EAV и JSON+typed projection, плюс явную domain schema для ограниченного профиля. Unbox помогает проверить, где динамическая универсальность не нужна, а не вынуждает выбрать один storage для всех проектов.
