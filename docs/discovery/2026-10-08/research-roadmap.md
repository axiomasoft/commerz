# Следующие эксперименты и вопросы для выбора архитектуры

2026-10-08. План продолжения исследования. Описанные ниже эксперименты **не выполнены**. В этой волне повторены только 16 иллюстративных проверок исходного аудита; их ограничения приведены в [chatgpt-audit-review.md](chatgpt-audit-review.md).

## 1. Решения с наибольшим влиянием

| ID | Вопрос | Текущие кандидаты | Нужное свидетельство |
|---|---|---|---|
| D01 | Первый профиль потребителя | Unbox-подобный сложный каталог; retail + склад; headless commerce | Два реальных user journeys с данными и ожидаемым результатом |
| D02 | Свойства | Domain schema; typed EAV; typed JSON + projection | Один набор данных и одинаковая семантика запросов |
| D03 | Inventory identity | Variant identity совпадает в ограниченном профиле; отдельный InventoryItem | Bundle/component/shared-stock сценарий |
| D04 | Резервирование | Адресное; общий pool с поздней allocation | Concurrent last-item + пересечение пулов |
| D05 | Tenancy | Одна установка/owner; shared scopes; отдельные spaces | Два consumer contexts в одном worker, импорт и очередь |
| D06 | Состав пакетов | Один артефакт; 3–5 пакетов с bridges | Две минимальные независимые установки |
| D07 | Plugins | DI strategies/registries; controlled model replacement; lifecycle manager | Два независимых плагина и порядок их регистрации |
| D08 | СУБД и версии runtime | Открыто; сверяться с актуальной экосистемой | Матрица потребителей и измеряемые required capabilities |
| D09 | Цены и скидки | Deterministic priority; best-combination; внешний authority | Полный расчёт с округлением и partial refund |
| D10 | История | Immutable accepted snapshots + amendments; event sourcing отдельных областей | Изменение каталога/плагина после продажи |

Не принимать D02 раньше, чем известны запросы D01. Не принимать D04 по схеме таблиц без конкурентных операций. Не принимать D06 только по количеству существительных в модели.

## 2. EXP-01 — сравнение фиксированного и динамического каталога

**Цель:** понять, что выигрывает при небольшом числе сложных характеристик, и где выигрыш исчезает.

**Данные:** ограниченный профиль Unbox после уточнения смысла «шесть», несколько семейств с несовпадающими definitions, sparse variants и составные свойства. Не генерировать миллион offers там, где предметно существует 30.

**Кандидаты:** explicit columns/child tables; normalized definitions/options; typed EAV; JSON+projection. Slots оставить контрольным вариантом, если их конкретный смысл подтвердится.

**Одинаковые задачи:** создать product; обновить одно значение; импортировать batch; прочитать карточку; выбрать допустимый variant; отфильтровать по диапазону и трём характеристикам одного варианта; facets после фильтра; локализованный fallback.

**Выход:** correctness fixture + query plans + rows scanned + query count + p50/p95/p99 + storage и стоимость изменения определения. Указать CPU/RAM, движок, версию, индексы, seed, объём и прогрев. Производительность без равной семантики не сравнивать.

## 3. EXP-02 — потерянная последняя единица

**Сценарий:** один item, один физический экземпляр; два магазина/канала, два pool, общий source. Одновременно заказывают по одной единице.

**Проверить:** общую границу блокировки/атомарного admission; pool membership change; retries; обратный порядок захвата нескольких items; нулевой stock; negative adjustment во время удержания.

**Критерий:** для строгого режима ровно одно подтверждённое обещание; второй получает объяснимый результат недостатка. Balances, reservation history, order и outbox согласованы. Успех одной транзакции и exception другой не должен оставлять чужой частичный резерв.

**Опровержение:** если реализация держит только два независимых pool locks, найти interleaving, где обе операции успешны. Сначала воспроизвести его, затем сравнить варианты authority/quotas/addressed reserves.

## 4. EXP-03 — временной резерв и внешний платёж

**Сценарий:** резерв до T; callback приходит после T; parallel expiry worker уже освободил remaining и другой checkout занял товар.

**Критерий:** система не подтверждает физически невозможное исполнение и не теряет сведения о полученных деньгах. Требуется явный исход: повторная попытка удержать запас, backorder по политике или компенсация оплаты. Нельзя просто бросить ошибку после факта payment.

**Вариации:** duplicate callback; consume одновременно с expire; extend со старой версией; частичная отгрузка до истечения остатка; clock skew; повтор после crash; очистка idempotency record.

## 5. EXP-04 — рецепт, единицы и transfer

**Сценарий:** один продаваемый bundle требует 2 × A + 1 × B, а корзина дополнительно содержит A. После quote изменяют рецепт. Одну составляющую перемещают между складами и частично принимают повреждённой.

**Критерий:** общая потребность агрегирована до резервирования; сохранён применённый рецепт; transfer не создаёт доступный товар одновременно в source и destination; damaged return не становится saleable; округление quantity не создаёт/не уничтожает единицы.

Профили preassembled bundle и virtual bundle проверить отдельно: это разные движения.

## 6. EXP-05 — последняя квота купона и возврат

**Сценарий:** coupon limit=1, два checkout, первый retry после таймаута, затем partial refund.

**Критерий:** только одно право удержано/использовано; replay не расходует дополнительную quota; applied amount и правила акции сохраняются; refund не пересчитывает скидку по сегодняшнему правилу.

**Вариации:** per-customer quota у guest/customer merge; купон выключен между quote и submit; expiry claim; multi-code одна promotion; total fixed discount распределяется на 3 строки; shipping discount; free item; refund одного из двух одинаковых units.

Нужно принять policy: quota возвращается при failed payment, отмене до исполнения, полном возврате или никогда. Это бизнес-решение, из названия таблицы его не вывести.

## 7. EXP-06 — два независимо написанных плагина

**A:** новый тип «размер с единицей» и range filter. **B:** новая акция по этому свойству + custom allocation priority.

**Критерий:** регистрация детерминирована, происхождение contributions видно, конфликт key/версии объясним. Config cache и долгоживущий worker не меняют результат. Ошибка плагина оставляет согласованную mutation.

**Вариации:** обратный provider order; duplicate type key; оба replace одной модели; неизвестный codec version; uninstall одного плагина после создания заказов; plugin отсутствует в read-only consumer; broken schema step.

**Архитектурный результат:** если хватает нескольких contract bindings, не вводить plugin manager. Если нужны dependency graph, compiled schema contributions и lifecycle, описать зачем каждый механизм нужен Commerz с конкретным failing case.

## 8. EXP-07 — эволюция схемы свойств

**Сценарий:** property decimal становится measurement, часть значений не конвертируется. Пока идёт backfill, старый worker пишет по прежнему codec, а поисковая проекция отстаёт.

**Критерий:** нет смеси, которую reader считает одной версией. Новая definition не объявляется активной до выполнения выбранного compatibility протокола. Есть resume и контроль последней записанной ревизии. Rollback либо доказан, либо операция честно объявлена forward-only с сохранением исходных данных.

Для ограниченной v1 альтернативой является запрет изменения типа и новая definition. Эксперимент может показать, что сложный live migration сейчас избыточен.

## 9. EXP-08 — импорт и смена владельца данных

**Сценарий:** внешний WMS отдаёт absolute stock; одновременно локально продают, приходит более старый snapshot и повторяются events. Затем WMS становится единственным stock authority.

**Критерий:** источник, режим full/delta, business timestamp и source version различимы. Старый snapshot не затирает более новый. Неполный full import не удаляет отсутствующие записи. Передача authority имеет точку переключения и reconciliation, а не бессрочный dual write.

Интеграция с конкретной 1С может стать одним adapter, но наличие её в старом аудите не утверждает обязательность для Commerz.

## 10. EXP-09 — consumer compatibility

Собрать два **изолированных** minimal consumer проекта после принятия профилей:

- Catalogue-only с собственным User, media adapter, фиксированной domain schema или набором attributes.
- Store + inventory + coupons с собственными actor IDs и tenant strategy.

Проверить install/migrate/upgrade, custom prefix, unsupported config, absence optional bridges, config cache, transaction connection, queue context, публичные DTO и совместимость независимых plugins. Нельзя выдавать успешный composer install за проверку всех сценариев.

## 11. Вопросы владельцу — следующая предметная сессия

Эти вопросы не блокировали текущий сбор материалов:

1. «Не больше шести» в Unbox — это список конкретных свойств на всю систему, максимум на product family или максимум осей варианта? Какие шесть примеров наиболее показательны?
2. Какие два проекта первыми реально будут использовать Commerz и в каком составе?
3. Нужны ли сразу дробные количества, партии, серийные номера, ячейки, сроки годности и owner/consignment?
4. Один physical stock продаётся несколькими магазинами? Можно ли split fulfillment и backorder?
5. Владелец цен и остатков — приложение или ERP/WMS? Какая задержка приемлема для витрины и для checkout?
6. Покупка только B2C или есть customer-specific prices, коммерческое предложение и оплата по счёту?
7. Можно ли ограничить первый публичный контракт одной СУБД и одним из tenancy modes?
8. Что считается успешным использованием купона и когда его лимит восстанавливается?

## 12. Программа второй волны источников

Приоритет выбирать по нерешённому вопросу, а не читать всё подряд:

| Вопрос | Следующие исходники |
|---|---|
| Families и PIM | UniPim; owning core Aimeos, а не только Laravel wrapper |
| Склад и операционный retail | AureusERP, NexoPOS; конкретные reserve/transfer/return flows |
| Купоны | Discountify, Couponables, Vanilo promotion execution path, Bagisto complete checkout path |
| Точное число/единица | Сравнение Money/decimal/UOM библиотек по API и существующим consumers |
| Plugin lifecycle | Два локальных конкретных extension сценария; Flarum/Concord только для нерешённых границ |
| История и документы | Explicit order amendments, partial refunds и inventory reconciliation |

Переход к реализации разумен, когда выбраны D01–D06, определены non-negotiable invariants и есть минимальный сценарий, опровергающий конкурирующие варианты. Остальные исследования могут идти параллельно вертикальным прототипам.
